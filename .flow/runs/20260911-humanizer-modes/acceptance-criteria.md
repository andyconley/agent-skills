# Acceptance criteria — approved
All cases must be tied to inspected inputs, outputs and explicit pass/fail observations. Static lint alone is insufficient. No universal word-count or AI-likelihood score.

1. Default engineering: a technical proposal with seeded mirrored rhythm is corrected; facts, caveats, identifiers and exact commands remain unchanged. Existing technical-protection and construction fixtures remain satisfied.
2. Personal preservation: a personal note with effective humor, first-person admission and useful digression retains those identified spans and progression; a seeded ambiguous/redundant span is fixed. Every changed span has a concrete editing reason.
3. Same construction, different modes: intentional clear rhetorical phrasing is retained in explicit personal mode; engineering removes it absent a technical protection reason. Personal audit does not report it as defective solely for its form.
4. Mode selection: no mode and generic 'more natural' retain engineering; explicit personal mode or clear equivalent activates personal; genre alone does not select it.
5. Protection: exact quote, command, citation, path and identifier survive both edit policies. Unknown facts are not replaced with invented specifics; evidence-supported corrections are disclosed.
6. Mixed content: an actual runbook with a conversational introduction retains engineering discipline. A personal narrative with an incidental command quote or list retains personal prose plus exact protected spans. Materially ambiguous purpose triggers a focused clarification.
7. Audit: engineering and personal audits each identify only supported defects, quote or locate them, and give repair directions without a replacement draft, source mutation or authorship score. Clean text produces no fabricated findings.
8. Strict personal: strict validation preserves legitimate personal constructions and catches truth/protected-content failures. Inapplicable engineering lint cannot mandate a voice change or be reported as passed. Exercise the available-check and unavailable-check paths honestly.
9. Portability and added patterns: weak generic assertion is diagnosed in context; supported abstract conclusion and necessary transition remain. Demonstrate both misuse and legitimate use of colons, trailing clauses and formatting.
10. Contract coherence: workflow, examples, shared-rule references and docs agree on priority, modes and strict behavior. Existing doc-flow-review fixtures and review-only scope remain unchanged.
11. Delivery evidence: in later implementation, appropriate repository validation and behavioral examples are recorded; README and invocation examples match the shipped contract. Live-runtime claims require actual live checks, not only file installation.
